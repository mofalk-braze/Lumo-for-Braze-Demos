# Project Instructions

- Maintain feature and capability parity between the iOS and Android demo-shell approaches. When changing pack application, runtime generation, asset packaging, launch flows, SDK bridge behavior, or Demo Cockpit controls for one platform, check the corresponding path on the other platform and either implement the analogous behavior or explicitly document why parity is not applicable.
- Treat demo packs as the source of truth. Applying a pack generates web runtime config, runtime manifests, synced assets, Android seed metadata, and iOS runtime defaults. Do not hand-edit generated runtime files.
- Keep `configHash` as the public configuration fingerprint and `runtimeHash` v2 as the active configuration-plus-assets-plus-private-app-surface deployment identity. Generate and package content for the active pack only.
- For an installed mobile app, treat its bundled runtime manifest's pack id as the target identity. Before changing a local customer pack, verify that identity and deploy only the same pack; never select a pack from a matching brand name or handoff directory.
- Treat the launcher host process as the sole state, orchestration, credential, and SDK-command authority. The Control Room is the admin, authoring, telemetry, and diagnostics client; Presenter Remote is a thin paired operator client limited to the active persona and at most seven approved controls, with no raw payloads or credentials.
- Keep Story Controls collapsed in the Control Room as a fallback. Do not package Presenter Remote as a browser extension unless three rehearsals show repeated window-focus or placement friction; any later side-panel wrapper must remain thin and introduce no authority of its own.
- Native shells own SDK execution. The web template talks to Braze only through the shared bridge contract; Android and iOS execute `changeUser`, events, purchases, push, and Content Cards through their native SDKs.
- Keep private pack `app-source/` and the fixed mirrored `screens/local-pack/` container ignored. Pack apply must mirror only `app-source/web-template/src/screens/local-pack/` into that working container and remove stale private code when the selected pack has no app surface. Expose a bespoke surface only through `screens/local-pack/pack-app.tsx`; tracked routes, ignore rules, and `App.tsx` must not contain imports, pack ids, or paths belonging to an ignored private pack.
- Keep REST API keys host-only. Resolve them from Control Room session state or environment variables, and never write them into web assets, Android resources, iOS source, demo pack JSON, or committed files.
- Treat SDK credentials as selected-pack state. Pack apply must clear generated Android SDK endpoint/key/FCM values when the active pack does not provide them, and launcher readiness must confirm the running native credential context belongs to that pack.
- Preserve SDK device identity by default. Any reset that clears app data, simulator/emulator state, or SDK storage must be an explicit recovery/testing action.
- Treat Android source URL overrides as Diagnostics-only development state. Keep the `DEV OVERRIDE` visible, accept only local Vite origins, and require bundled mode for rehearsal and handoff. Do not imply iOS parity while iOS is already dev-server-only.
- Treat native source readiness as rendered-page proof, not URL or runtime metadata alone. On both platforms, readiness requires main-frame completion and JavaScript `webReady` to agree on the same canonical source generation. Before accepting `webReady`, native must validate protocol, runtime id, config hash, and runtime hash against its canonical bundled/generated runtime; terminal telemetry retains launcher/execution correlation.
- Keep native render evidence monotonic. Delayed iOS callbacks from an older `webReady` session or render generation must not replace newer failure evidence. Stopping the live-web host never proves Android cleared its native override; persist the hazard until correlated bundled-source evidence clears it.
- Preserve the non-secure Android Swipe keyguard for lock-screen notification demos. The runner enforces and verifies shown, private, silent, non-minimal lock-screen notification settings plus any tap-to-wake setting exposed by the expected AVD. Never store, hardcode, guess, or type a device PIN; a secure credential requires one-time manual migration to Swipe.
- Keep source distribution first. Team members should be able to clone the private repo, provide local credentials, run the Control Room locally, and build Android/iOS without relying on committed generated state.
- Before committing, run `npm run check:precommit`, `npm run public:check`, and `cd web-template && npm run build`. If platform code or launch flows changed, also run the relevant Android and/or iOS build checks.
